# RGBA 原理与开销

## 颜色不是最终显示颜色

“RGBA 版”是发行名称，不代表四个通道全可自由塞数据。文字颜色载荷使用 RGB；A 保持 255。Shader 只有在 GUI、纹理标记和颜色门控同时满足时才解码，最终从调色表还原可见颜色。

```
文字 RGB = 0xD40000 | (top << 8) | paletteIndex
文字 A   = 255
字形纹理标记 RGB = 0x174783

图片 RGB = 0x800000 | ((width - 1) << 14)
                      | ((height - 1) << 5) | (localY & 31)
width / height = 1..512
localY = -8..8
```

图片宽和高各需 9 位，行内 Y 分配 5 位，加上识别位装入 24 位 RGB。两个 1..512 不是“1024 个通道”，而是两项各有 512 种取值，共 512×512 种宽高组合。

## 换行和行内偏移

仍然利用原生正文行组织位置，安全时用真实换行进位，局部再做偏移。为了保留混合图片/文字的全局 z 顺序，行计划并非简单对所有 Y 取模；跨行图层需要时仍使用字体基线锚点。

plain_message 行步长为 9px，但独立控件还有上下留白和控件间距。不能把两个独立正文控件的起点差当成一个字形行高。

## 为什么点击没有跟着 Shader 丢失

原版 CPU 命中不理解 Shader 对顶点的移动。因此可见字形之外，还生成透明度很低的原生代理字格，文字与图片分别集中到 `text_hit_all.json`、`image_hit_all.json`。代理随实际位置和尺寸准备，不恢复独立 backend 区域。

## 省在哪里，仍花在哪里

- 整字按字号共享，不因新增一个 Y 偏移重新复制一套汉字 PNG。
- 同一自有图片的 wrapper 可服务不同宽高，避免逐尺寸复制源纹理。
- 更多字号、倍率、字符、颜色、不同源图和变体仍会增加资源；fallback 图形路径也有成本。
- 行计划、原生命中代理、字体 JSON、ZIP 和客户端字体缓存仍然存在。

没有一个脱离布局的“每加偏移固定增加多少 KB”。要比较大小，应使用同样的布局、字符、倍率、合包方式和压缩设置，并同时检查实际显示与点击。
